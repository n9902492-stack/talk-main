# Meeting recording and transcription

This adds to the existing Talk meeting, authentication, moderation and PostgreSQL/SQLite systems. It does not provision or deploy infrastructure. Production capture is opt-in.

## Local use

1. Install dependencies with `npm ci`.
2. Install Google Chrome. Run `npm run recording:setup` once on Windows x64. This downloads the checksum-pinned official whisper.cpp v1.9.2 executable, fast multilingual base model and separate multilingual medium-q5_0 Hindi model into ignored `data/transcription`. The MIT license is saved with them. No recording is uploaded to an AI service. Hindi accuracy mode is substantially slower on a CPU.
3. Start the existing LiveKit server with `npm run meeting:server`, then `npm run dev`. Open http://localhost:3001. Both browsers need their own authenticated Talk accounts.
4. Join the same meeting. The host/co-host opens **More options → Recording & transcription**, chooses **Audio only** or **Screen, cameras & audio**, English/Hindi/detection and retention, then **Request recording consent**. For screen recording, use **Share screen** in the meeting; the video mode includes shared screens alongside participant cameras and meeting audio. It cannot capture a screen that nobody shares.
5. Every connected user must explicitly consent. **Start Recording** rechecks consent and authority on the backend. New users consent on the existing pre-join screen before receiving meeting access. Declining blocks capture; withdrawing consent stops the current segment. Recording is visibly indicated to everyone.
6. **Stop Recording** acknowledges with HTTP 202 immediately after authorizing the state change. Saving continues in the background; wait for the completed status before playback. Pause/resume is unsupported: stop and request a new segment, with fresh consent, to continue.
7. Open **Meetings** in the workspace, then the meeting. Recording and Transcript tabs provide private playback, transcript search, timestamp seeking, TXT/PDF exports, retry and deletion.

## Capture architecture

### Local recorder preparation and startup errors

Run `npm run recording:prepare` in a normal terminal after installing/updating dependencies or changing the recording client. This creates a Git-ignored bundle in `backend/dist/recording`. The runtime verifies its source/dependency fingerprint and content hash before using it. It can then start capture without invoking a compiler in a restricted filesystem environment. Without a valid artifact, unrestricted runtimes retain the existing in-memory build fallback; compilation failure produces the explicit `recording_bundle_failed` status with preparation instructions before any capture browser or partial file is opened.

Stopping now distinguishes encoder flush (`stopping`) from private-file finalization (`processing`). The backend checks the committed file/object size before persisting `completed` (shown as Ready). Managers see Processing and saving failures in the meeting and details; a successful HTTP acknowledgement alone is never presented as a saved recording. Existing records, consent rules and storage keys are unchanged.

The local recording profile is 1280?720 at a conservative 15 fps, targeting 4.5 Mbps video and 128 kbps audio. Camera images fill their tile with overlaid name labels, preserving more source detail. Higher bitrate increases file sizes and can reach the existing 512 MiB segment cap sooner. A 100 ms silent Web Audio buffer protects sample continuity under encoding load.

The existing self-hosted LiveKit installation has no Egress service. Talk therefore uses a server-owned Chromium subscriber, not the host's microphone or screen. The worker receives a short-lived, read-only, room-restricted LiveKit token and subscribes only to backend-authorized, consenting identities. It uses a dedicated read-only subscriber transport and a shared silent Web Audio sink with LiveKit playout attachments, then mixes all subscribed audio tracks with Web Audio and optionally composites video/screen-share tracks into a 1280×720 canvas at 15 fps. MediaRecorder writes WebM chunks to a bounded private file; FFmpeg remuxes without re-encoding to add playback duration and seeking indexes. The `Talk Recording` subscriber is visible. No native Egress or provider pause API is claimed.

Worker callbacks and repeated stop requests are idempotent. Capture ownership is leased in the database. A lost worker is marked failed, its SFU subscriber is removed and partial output is discarded; incomplete recordings are not presented as completed. Ending a meeting or losing all human participants stops capture. The UI polls authoritative backend state and also refreshes on server LiveKit notices.

## Data and processing

- SQLite migration 007 and PostgreSQL migration 005 add recording metadata, per-segment/account consent, moderation audit events, durable jobs and transcript segments. No alternate account/session system is created.
- Local files stay under ignored `data/recordings`, outside static assets. Downloads/playback pass through current authenticated host/co-host authorization, including byte-range requests. Revoking a co-host also revokes access. Private responses use no-store.
- A leased asynchronous job extracts 16 kHz mono PCM with FFmpeg, then runs the real local multilingual Whisper model. Up to three attempts use backoff; expired job leases recover after restart. Encoder finalization, remux/upload and transcription run in independent database contexts after HTTP 202 responses, so closing the initiating request cannot strand a recording. Stale transcription results are discarded after lease ownership changes.
- Segments contain start/end times and language metadata. Mixed room audio does not establish a reliable speaker identity, so speakers are explicitly unattributed. English and Hindi are supported by the multilingual model; transcription is fallible and should be reviewed.
- TXT is UTF-8. PDF uses isolated Chromium, escaped text, no JavaScript/network and Unicode fonts. Export has a deadline.
- Limits: 2 hours / 512 MiB per segment, 2 GiB stored per meeting owner, two concurrent captures, at most 16 people for video mode, one globally leased transcription job across backend instances sharing the database. All allowed audio tracks are mixed. Canvas renders up to 32 video/share tracks. Recording retention is 7, 30 or 90 days. Deletion immediately revokes access and removes transcript rows, with durable file cleanup.

## Stop, restart and CPU scheduling

The owned Chromium worker ends generated canvas/audio output tracks before stopping MediaRecorder, waits for its final data event and pending file writes, syncs/closes the file, then remuxes it. Encoder flush has a 20-second client deadline (25 seconds at the worker boundary). Browser close has a 3-second grace period followed by a bounded kill of that worker's own process tree. Temporary indexed output is removed after failure or cancellation.

The service bounds startup at 90 seconds and complete stop/save at 180 seconds. These are failure ceilings, not expected waiting times for the Stop button. Incomplete output fails closed and is never exposed as a completed recording. Lost/NULL capture leases, abandoned speech jobs, and inconsistent processing metadata are reconciled by the background poller after restart. A sudden OS or power failure cannot restore encoder data that was never flushed; recovery makes that failure explicit and schedules private-file cleanup.

Whisper waits at least 15 seconds after capture completion and does not start while an active capture is using the shared database. A database lock and renewable job lease enforce a single recognition job across instances. FFmpeg preparation and Whisper run at below-normal OS priority where supported, with two threads by default (`WHISPER_THREADS`, capped at four). This is best-effort scheduling, not a CPU reservation or a guarantee on small machines. An open meeting without recording does not defer transcripts forever. Use a separately sized persistent worker before production load testing. Speech jobs have a 63-minute total deadline, up to three attempts with backoff, and cancellation on backend shutdown. The viewer reports queue/retry/processing/completed/failed states; no invented percentage is shown.

Explicit English uses the installed multilingual small-q5_1 model when available, otherwise the base model. `WHISPER_ENGLISH_MODEL_PATH` can explicitly select an English model; an existing global `WHISPER_MODEL_PATH` remains authoritative unless that English override is set. No model is downloaded automatically. Explicit Hindi uses the local medium-q5_0 model when installed, or an explicitly configured `WHISPER_HINDI_MODEL_PATH`. Automatic language selection first runs a bounded detection-only pass with the lighter model, then selects English or Hindi. An existing custom global `WHISPER_MODEL_PATH` is preserved unless a separate Hindi path is configured. Without the accuracy model, base-model Hindi can be romanized and inaccurate. Transcripts must be reviewed: the actual native Hindi sample still had recognition errors. The measured CPU accuracy-model run took 12m51s for 22.7s of speech; this machine is unsuitable for timely long Hindi transcripts. Long-meeting throughput, GPU acceleration and a suitably sized production worker are not verified. Processing has a deadline and can fail rather than run indefinitely.

## Optional private cloud storage

Set `RECORDING_STORAGE=gcs` and `RECORDING_GCS_BUCKET` only after approval. No bucket is created automatically. The existing backend identity uses Application Default Credentials with least-privilege object create/read/delete and bucket metadata-read access. The bucket must enforce uniform bucket-level access and public-access prevention. No public ACL, public playback URL or service-account credential is sent to browsers. Downloads are proxied after Talk authorization. Configure a bucket lifecycle as a defense-in-depth cleanup policy; database retention remains the access authority. Backups and object versions require their own retention policy.

## Production prerequisites — not deployed

Production defaults to `RECORDING_PROVIDER=disabled`. To enable capture, approve a persistent worker host with CPU/memory, network access to the existing LiveKit SFU, Chromium sandbox support, FFmpeg, fonts, platform-matching Whisper executable/model, and private durable storage. Use the existing PostgreSQL account/session database and run migrations before traffic. Moving existing local recordings to object storage requires a separate private file migration in addition to the database metadata import. A durable mounted volume can use `RECORDING_DURABLE_VOLUME=true`; ephemeral container storage cannot.

The prepared backend Dockerfile includes Chromium, FFmpeg and Unicode fonts. Production must explicitly set `RECORDING_PROVIDER=local-browser`, `CHROMIUM_PATH`, `FFMPEG_PATH`, `WHISPER_EXECUTABLE`, `WHISPER_MODEL_PATH`, optionally `WHISPER_HINDI_MODEL_PATH`, and private storage settings. The container and actual PostgreSQL/GCS deployment require environment-specific validation. Recording is unsuitable for a request-only container that suspends CPU or scales to zero during capture. Do not enable untrusted browser sandbox bypasses. This is a small-meeting implementation, not a distributed Egress deployment.

Costs are not activated by this code. Production worker compute, existing LiveKit bandwidth, private object storage/downloads and database usage can be billable; approve infrastructure and limits separately. Local Whisper has no per-minute API fee but consumes CPU and may process slower than real time. No paid AI API, hidden capture, recording deployment or cloud resource creation occurs automatically.

## Checks

- `npm run test:recordings`: backend authorization, consent, retention, jobs, exports, token and processing-validation tests. Media/transcript providers in unit tests are explicit fixtures.
- `npm run test:recordings:browser`: actual installed Chrome browsers and local LiveKit transport, server capture, decoded audio frequency/video pixel checks, late-join consent, withdrawal, genuine local Whisper job, history/search/seek/export and mobile layout. Cameras, microphone input and test authentication are fixtures, not physical devices or real Google login. Synthetic-tone tests explicitly disable audio noise processing only in the test browsers to keep deterministic frequency measurements.
- `npm run test:transcription:real`: genuine local Whisper recognition of English JFK speech and human Hindi speech from Google's CC-BY-4.0 FLEURS dataset. Only a bounded archive prefix is read to extract one checksum-pinned Hindi clip. Fixtures, source attribution, hashes, recognized text and per-language timings are recorded in `artifacts/qa/real-transcription-results.json`. This is not a simulated transcript. Failed sample attempts remain separate evidence; a model producing poor romanized Hindi on another sample is not a successful Hindi check.
- `npm run test:auth:production`: an isolated local PostgreSQL 16 Docker container exercises authentication plus recording metadata, jobs, consent, private access and application/pool restart. Recording providers in these database tests are fixtures; they do not prove media capture. The runner does not connect to a production database or create cloud resources.
- Existing authentication/media/effects tests, `npm run lint`, `npm run build` and production database checks remain relevant. A skipped PostgreSQL check is not a verified PostgreSQL deployment. See ignored `artifacts/qa` for current browser evidence; consult the final implementation report for which checks actually passed.

## Remaining limits

No pause/resume, reliable diarization, native Egress integration, cloud transcription, live captions, AI summaries or automatic transcription accuracy guarantee. Browser compositing and CPU speech recognition need capacity monitoring before production. A sudden machine failure cannot recover unflushed browser encoder buffers. All meeting participants must be informed of the configured retention and access policy; metadata/consent audit records follow the application's database backup policy.
